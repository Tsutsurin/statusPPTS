# STATUS с нормализацией названий

ИИ применяется перед сопоставлением только для названий вендоров и
продуктов. Статусы и ID ППТС определяет существующий STATUS по кандидатам,
баллам, журналу и базе знаний.

Парсеры запускаются отдельно. STATUS принимает их готовые XLSX/CSV
через флаг --tsu.

## Подготовка

```powershell
py -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item config\normalization.example.json config\normalization.json
```

В config/normalization.json заполните:

- url — полный URL API Chat Completions;
- model — имя модели;
- enabled — true для использования ИИ;
- api_key_env — имя переменной окружения с ключом API.

Для текущего сеанса PowerShell:

```powershell
$env:STATUS_AI_KEY = 'ВАШ-КЛЮЧ'
```

Если API работает без авторизации, задайте api_key_env пустой строкой.

Пути prompt_file и cache_file задаются относительно файла конфигурации
или абсолютными путями.

В примере enabled выключен. При выключенном API применяются очистка
пробелов и подтверждённые алиасы.

## Запуск без нормализации

```powershell
python tools/status_json.py --tsu fstek.xlsx --tsu news.xlsx --ppts-general ppts.xlsx --out baseline.json
```

## Запуск с нормализацией

```powershell
python tools/status_json.py --tsu fstek.xlsx --tsu news.xlsx --ppts-general ppts.xlsx --normalize-config config/normalization.json --out normalized.json
```

Можно добавить прежние параметры:

- --ppts-local;
- --journal;
- --kb;
- --app-config.

Режимы llm, recall и app задают настройки существующего сопоставления.
Они не поручают модели постановку статусов.

Для сравнения baseline и normalized используйте одинаковые режимы,
настройки и входные файлы.

## Логика работы

1. Читаются результаты парсеров и ППТС.
2. Продукты разбираются на пары вендор, продукт и версии.
3. Очищаются пробелы.
4. Проверяются подтверждённые алиасы и кэш.
5. Неизвестные названия отправляются в ИИ.
6. Ответ проверяется на полноту записей, формат и сохранение чисел.
7. Нормализованные названия передаются в существующее сопоставление STATUS.
8. STATUS выставляет статусы по своей логике.
9. Результат сохраняется в JSON.

ИИ получает только названия вендоров и продуктов. ID ППТС и статусы
в запрос не передаются.

При uncertain или unchanged сохраняется исходное название после
очистки пробелов. При ошибке API или формата запуск останавливается.

Версии в отдельных полях, CVE, CVSS и ссылки не изменяются.

## Результат

В итоговом JSON сохраняются:

- product_raw — исходный продукт из таблицы;
- pairs — нормализованные пары и исходные версии;
- name_raw и vendor_raw — исходные названия кандидатов ППТС;
- normalization — изменения, решения и обоснования;
- status — статус, рассчитанный STATUS.

## Подтверждённые соответствия

Добавляйте проверенные пары в массив confirmed_aliases конфигурации:

```json
{
  "vendor": "Red Hat Inc.",
  "product": "Red Hat Enterprise Linux",
  "canonical_vendor": "Red Hat",
  "canonical_product": "Red Hat Enterprise Linux"
}
```

Алиасы применяются до обращения к модели, независимо от регистра
и лишних пробелов. Не используйте их для удаления версий или редакций.

Ответы ИИ в кэше не являются подтверждёнными соответствиями.
Проверка формата не доказывает смысловую эквивалентность названий.

## Проверка точности

Сравните baseline.json и normalized.json на уязвимостях,
которые уже проверены вручную.

Автоматическое обучение порогов на статистике не реализовано.
Баллы существующего алгоритма не являются вероятностями.

## Тесты

```powershell
python -m unittest discover -s tests -v
```

Тесты проверяют:

- одинаковую нормализацию ППТС и данных парсера;
- сохранение версий и исходных названий;
- обработку uncertain;
- отклонение изменения чисел;
- отклонение полей статуса в ответе ИИ;
- работу кэша;
- полный запуск STATUS с локальной нормализацией.

Для сборки EXE обновлён tools/status_json.spec.
Конфигурация и файл промпта передаются отдельно.
